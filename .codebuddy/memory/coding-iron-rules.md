# 编码铁律（跨项目通用 · 作者：袁燕）

> 最后更新：2026-08-08 | 来源：智能柜 Qt 项目 work-rules.md 提炼 + GJB5000B 平台框架新增
> 适用范围：所有项目（Qt/C++、前端、Python 后端、文档原型）

---

## 一、修改前三轮分析（强制）

任何代码/文档修改前，必须先做三轮分析再动手：

1. **需求分析** — 理解真正要解决的问题，有无隐含需求？
2. **影响分析** — 改动影响哪些文件/模块/页面？是否破坏现有功能？
3. **举一反三** — 同类问题在项目中是否还有别处存在？

原则：代码尽可能简单明了，最小改动，不引入不必要复杂度。禁止直接跳入编码。

## 二、举一反三铁律（强化版）

每次修改一个文件/页面/模块，必须立即检查：

- [ ] 还有哪些文件/页面/模块存在同样或类似问题？
- [ ] 修改是否影响其他依赖方？检查所有引用和调用方
- [ ] 字段名、状态值、API 路由是否在所有地方一致？
- [ ] 同类空指针/野指针/undefined 问题是否在其他地方也存在？
- [ ] 修复 UI 问题后，全局搜索类似 UI 模式
- [ ] **禁止局部修复导致项目不一致**

## 三、命名规范（铁律）

- **全项目统一驼峰命名（camelCase）**：变量、函数、前端字段、JSON 键名一律驼峰。
  - 反例（禁止）：`flow_no` / `borrow_time` / `tool_name`（蛇形）
  - 正例：`flowNo` / `borrowTime` / `toolName`
- 数据库层内部可用 snake_case（SQL 列名），但 **DAO/Service 返回给上层必须转驼峰**。
- 禁止 a/b/c 等无意义单字母变量，必须用业务语义命名（如 `alertLog` 而非 `a`）。
- 常量/配置键：前端用驼峰常量，后端 Python 用 UPPER_SNAKE 模块内常量（语言惯例），但对外 JSON 接口一律驼峰。

## 四、编码格式与注释

- 文件头写明作者**袁燕**，禁止 AI 化语言（不写"作为一名 AI"之类）。
- 关键函数必须标注：**输入参数、输出返回值、功能说明**。
- 每次修改注释写清改动原因（不堆历史版本号，只体现最终功能）。
- 无测试代码混入正式代码。
- 临时文件放 `temp/` 或 `F:\tempFile`，不进工程目录、不提交 Git。

## 五、最小改动原则

- 只修改必要部分，不过度重构、不大篇幅重写用户大文件。
- 用精确修改（replace）而非整体覆写。

## 六、修改后自检与测试（强制）

- [ ] 代码符合规范、保持专业度
- [ ] 关键函数清晰标注输入输出和返回值
- [ ] 文件头作者袁燕、无测试代码混入
- [ ] 自行验证可编译/可运行（必须实际执行构建或运行命令）
- [ ] 修改前预判 3 个以上潜在风险并提前规避

测试要求（高级测试工程师级别）：

1. 单元测试
2. 配置项测试
3. 系统测试
4. 修改后必须再次测试验证直至无问题
5. **禁止只编译/只语法通过就认为没问题**

前端额外：功能测试（实际运行看效果）、边界测试、交互测试（按钮/输入响应）。
HTML 原型额外：改完用 Node 注入 DOM stub 实跑渲染函数 + preview_url 实际查看渲染。

## 七、架构分层铁律（高内聚低耦合）

- **数据层 / DAO 层**：所有 DB 操作（SELECT/INSERT/UPDATE/DELETE）只能写在 DAO 或数据层，禁止在 pages/UI 层直接写 SQL。
- **Page/UI 层**：只负责交互和调用 Service/DAO，不写数据访问逻辑。
- **前后端解耦**：只通过 JSON API 通信，互不知道对方语言；字段命名前后端一致（驼峰）。
- **模板与代码解耦**：文档模板（A1~A83）独立为母本 docx + JSON 映射配置，加模板不动代码。
- **依赖倒置**：上层依赖抽象接口，数据来源（静态 JSON / 真实 API）可切换，只改 data 层一个地方。

## 八、脏数据铁律

- 代码绝不写数据修复/一致性校验函数（如 fixDataConsistency/cleanData）。
- 数据不一致直接用 SQL/DB 命令修复，代码只负责业务逻辑。

## 九、Git 提交规范

- 只提交代码文件；temp/、build/、.vs/、*.user、安装包、二进制一律不提交。
- 禁止 `git add .` / `git add -A`，必须精准添加。
- 提交前 `git status` 确认暂存区；提交信息简洁中文。

## 十、全局思维

作为高级技术总监，修改一个页面必须全局检查所有类似问题，避免局部修复导致项目不一致。包括前后端字段命名一致、状态值与 schema 对齐、API 路由正确指向。
