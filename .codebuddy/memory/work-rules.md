# 编码铁律与测试要求

> 作者：袁燕 | 创建：2026-08-10 | 跨会话生效

## 1. 修改前三轮分析（强制 SOP，禁止跳入编码）
> 来源：继承智能柜 coding-iron-rules.md §一/§二。袁总 2026-08-27 重申：每次改东西前必须做充分的需求分析 + 影响分析，再动手；且每次修改必须具备举一反三能力。

任何代码/文档修改前，**必须先在回复里写出以下分析，再动手**（口头/书面都算，但必须显式做）：

- **第一轮 需求分析**：袁总真实要解决的问题是什么？有无隐含需求？（如"卡处理中"背后可能是前端 Promise 逻辑、也可能是服务端进程污染，先定位再定方案）
- **第二轮 影响分析**：改动影响哪些文件/模块/页面？是否破坏现有功能？调用方/被调用方会不会受牵连？
- **第三轮 举一反三（强制）**：同类问题在项目中是否还有别处存在？本次修复能否做成通用能力？别处是否也该一并修？
- 原则：最小改动、代码简单明了、不引入不必要复杂度。

**举一反三检查清单（每次修改必勾）**：
- [ ] 还有哪些文件/页面/模块存在同样或类似问题？
- [ ] 修改是否影响其他依赖方？检查所有引用和调用方
- [ ] 字段名、状态值、API 路由是否在所有地方一致？
- [ ] 同类空指针/undefined/超时挂起问题是否在其他地方也存在？
- [ ] 修复 UI 问题后，全局搜索类似 UI 模式
- [ ] 本次修复能否沉淀为通用模板/铁律，避免下次重踩？（如：多 worker 清理、前端缓存破、异步超时兜底）
- [ ] **禁止局部修复导致项目不一致**

## 2. 验证铁律（修改后必须实跑验证才结束）
- 前端拆分：用 Node 注入 DOM stub 实跑渲染函数（如 Pages.base()），不靠 node --check（语法对≠运行不崩）
- 预览：preview_url 打开实际查看渲染（可见性/触屏/四色一致）再回复
- 后端：curl 真实 HTTP 验证 CRUD 闭环 + 400 校验
- 禁止只编译/语法通过就交差

## 3. 触屏优化标准（继承智能柜）
- 按钮 ≥48px，圆角 12-14px，字体 16-18px
- 输入框高度 48px，字体 16px
- 统一表单控件，颜色对比清晰

## 4. 分层与解耦（继承智能柜 P18）
- 前端绝不直连 DB；取数只走 Api 封装（HTTP+JSON）
- 前端按页面解耦：js/pages/<id>.js 各管各页，css 拆 common.css + css/pages/<id>.css
- 字段统一驼峰（reqId）；ORM/DB 内部蛇形（req_id）（P13）
- 路由不降级：无效参数返回明确 400，不静默返回错误数据（P10）

## 7. 脏数据铁律（继承智能柜）
- 代码层绝不写数据修复函数；不一致直接用 MySQL 命令修复

## 8. 数据库与 Git 同步铁律（袁总 2026-09-02 指令）
- **每次 git 提交（含 push 到远端）前，必须重新导出最新 MySQL 库 gjb5000b**，保证 clone 可还原全部文档数据。
- 导出命令（结果文件 `database/gjb5000b.sql`，已随上次提交入库，未被 .gitignore 忽略）：
  `mysqldump --user=root --password=root --host=127.0.0.1 --port=3306 --default-character-set=utf8mb4 --single-transaction --routines --events --result-file=database/gjb5000b.sql gjb5000b`
- 提交时必须 `git add database` 一起提交；数据库变更与代码变更同批入库。
- 说明：`gjb5000b.sql` 含全量真实业务数据（R105/顾客/人员/签署），仅适用私有/可信仓库，公开前需改 `--no-data` 仅结构版。
